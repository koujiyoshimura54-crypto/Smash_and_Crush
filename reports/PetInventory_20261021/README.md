# Pet Inventory and Studio equipment preview — 2026-10-21

## Findings

**Missing display was not reproduced for legitimately owned target Pets.** The current saved Inventory enumerates `state.Owned` by individual copy ID, not World1 Config.Pets or Merge eligibility. A fixture containing all 42 target species, a World1 normal Dog, a second W2 Dog and an unknown retained species produced **45 server-owned copies, 45 received copies and 45 Inventory cards** before this fix. All 42 target species resolved to the correct runtime models. There were 43 actual model viewports including the duplicate W2 Dog; Dog uses its existing icon and the deliberately unknown specimen retains its title/ownership with an expected missing-icon warning. No target species was filtered by World, Limited status or Merge membership. The original display paths therefore remain unchanged.

The user's actual persistent profile was not read or modified. A purchase prompt or hatch presentation alone cannot prove ownership. In particular, the known override refusal prevents a normal hatch from committing, and an override can defer a new Limited receipt grant. Such an operation has no newly owned copy for Inventory to display. That explains a supported route to apparent missing Pets, but it is **not proof that every user-reported missing specimen followed that route**. No recovery grants or ownership fabrication were added.

**Equipment refusal was confirmed independently.** In baseline Play, World1 Limited Pet_042 equipped normally through an actual Inventory click and the authoritative multiplier became 1.9. Sending the actual `/test level 160` command through TextChatService activated the existing StudioStartController/ApplyStudioStartLevel path. The 45 cards and 43 viewports remained present, but clicking another owned Pet did not change equipment. The existing `PlayerDataService.MutatePets` snapshot guard rejected equipment along with purchases, as established in `47decb4`. One direct plugin-context require returned DataNotLoaded because that context has a separate module cache; that response was not used as evidence of the live handler's rejection.

## Implemented behavior and changed Full Paths

Only four existing Sources changed:

| Full Path | Change |
|---|---|
| `ServerScriptService.Services.PlayerDataService` | On the first Studio level override, copy the validated committed Pet state into a separate session-only `StudioPetPreview`. While that override exists, permit **Equip only** against owned preview copies using the existing Pet.ApplyOperation request/revision/toggle rules. No durable Pet collection, pending purchase, receipt marker or Win is changed by preview equipment. GetPetState returns the active view. Restore discards the preview and republishes the committed equipment. Reject entering the override during a pending item transaction. |
| `ServerScriptService.Services.PetServer` | Use the authoritative preview equipment for the existing Strength multiplier only while Studio plus the level override are active. Continue enforcing owned copy ID and available model for every equipment request. Propagate the view generation. |
| `ServerScriptService.Services.EggServer` | Include the server's Pet view generation in state responses and forward it with mutations. Reject requests from a previous preview/normal view before receipt shortcuts, so a delayed equipment request cannot toggle a later session view. Normal hatch validation and durable transactions are retained. |
| `StarterPlayer.StarterPlayerScripts.Services.PetClient` | Refresh when the output PetViewGeneration attribute changes, send that generation with requests, and reject stale responses from previous generations. Allow the lower committed Pet revision when leaving a preview; this restores the actual Inventory selection/check/color instead of retaining the newer temporary revision. |

The snapshot remains server-memory state. Neither client attributes nor a client success message authorize ownership. An existing owned GUID selects the model; the model name is never substituted for the GUID. Unknown species remain owned, and an unavailable/foreign copy cannot be equipped. Per-copy counts and the existing one-equipped-Pet rule are unchanged. Repeating a level override retains the same original snapshot/preview; reset restores the original view. Release removes the whole session. Ordinary Save still exits with StudioRuntimeOverride while the level override is active.

Normal Egg purchasing under an override remains **StudioOverrideActive**, as requested. Paid GrantLimitedEgg retains the same rejection and durable Receipt/Policy/ownership protections; no paid purchase was enabled or acknowledged through the preview path. Limited Egg 02 remains Product 3720640383, base 279 Robux, Open 1 / one Pet. Merge, prices, model assets, odds, effects, layout and World progression were not changed.

## Focused validation

The accepted baseline and modified Play runs used the actual current place in one task-owned Studio with a real local client. Temporary memory DataStore, Marketplace and Policy adapters isolated all writes and mock receipts. The unpublished local-file receipt context/creator checks were substituted only inside the temporary test environment, as in the earlier paid-Pet tests; the production checks are restored. The first fixture startup was stopped to add its missing adapter RemoteEvent before accepted validation; those fixture errors are not attributed to the game.

- **Ownership → transport → cards:** 45 initial server copies matched 45 received copies/cards. All 42 targets resolved to real models with PrimaryParts and actual viewport geometry. The unknown fixture did not stop later cards. No current-World filter was found. World1 normal display was retained as a comparison.
- **Normal actual clicks:** equip/replace/unequip passed for World1 normal, World1 Limited, World2 normal and World2 Limited. Two separate W2 Dog copies were selected in turn by GUID. Existing checks and equipped colors followed the selected individual. Representative authoritative multipliers were Dog 1.02, World1 Pet_042 1.9, W2 Dog 1.6 and W2 Pet_042 2.9. These are real PetServer multiplier outputs, not a measured long Training session.
- **New grants and update:** one real normal EggServer hatch plus one simulated receipt through the real ProcessReceipt for each Limited product increased owned/received/card counts **45 → 48**. Each receipt replay returned PurchaseGranted without adding a copy. Actual client hatch interactions were completed before further Inventory clicks. This verifies mock fulfillment and UI update, not actual billing.
- **Actual level command:** `/test level 160` went through the engine TextChatCommand and existing controller. The modified server created a preview and the client refreshed its generation. Actual Inventory clicks equipped/replaced/unequipped the four comparison categories. Preview effects and one follower reflected the active selection.
- **Save isolation:** across preview equipment operations, all durable Pet fields compared equal to the original snapshot and the memory-store write count stayed unchanged. Explicit Save returned StudioRuntimeOverride with write delta **0**. A final isolated Save/Release probe also wrote **0**, discarded the preview and retained the original 48-copy durable inventory/equipment. No preview operation entered a durable pending mutation or receipt journal.
- **Reset and delayed messages:** `/test reset` removed the preview and restored committed equipment, Pet/Pet2 mirrors, multiplier and follower state. The client accepted committed revision **49** after temporary revision **58** because its generation changed. An old-generation request returned PetStateChanged. Repeating the same preview request returned AlreadyApplied without a second toggle. A subsequent normal equipment request committed through the existing save path.
- **Negative ownership:** nonexistent and simulated other-profile copy IDs returned PetNotOwned both normally and during the preview. The other owner was an isolated memory fixture, not an actual second client. A valid paid-grant probe during the override returned StudioOverrideActive. A normal hatch under the override remained rejected.
- **Lifecycle:** actual Humanoid death/automatic respawn and World1/World2 round trips via the existing `/test world` travel commands retained ownership/equipment in normal and preview states. Final follower count was **1**, and the actual follower mesh signature matched assigned model **Pet_107**. A background/inactive Studio temporarily stopped client rendering and left a follower unparented; activating the owned window restored RenderStepped and the one follower. No follower Source change was necessary. Commands attempted while the character was dead were retried after respawn; those early errors were not counted as travel passes.
- **Save/reload:** real PlayerData Save/Release/Load against the memory store retained all **48 copies** and the selected equipment. This is simulated persistence, not a production disconnect/rejoin. Manual Release/Load in the same fixture client is not used as a new-client transport test.
- **Source/persistence:** all four changed Sources compile with the local Luau compiler. The cleaned native Edit Sources match expected normalized lengths/checksums. The same-file writer decodes the written file again and exactly matches all four saved Sources. It verifies **4,915,670** existing property values and preserves every other Source, instance, parent and setting; see [Writeback.json](Writeback.json).

The existing sound authorization warnings and Roblox Core UI warnings were outside this change. No changed-production-code runtime failure remained in the accepted run. Probe failures caused by an unfinished hatch, hidden menu or paused background rendering were retried under the correct visible/active state rather than reported as game passes.

Not verified: actual Robux billing, real Roblox receipt delivery, production persistence/rejoin, actual two-client foreign ownership, production gate portals or additional device layouts. No production data was granted, reset or modified. The user profile's exact suspected missing copy IDs remain unverified.
