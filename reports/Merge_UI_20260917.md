## Before

The client created one card per owned copy, retained session-local copy serials, and required three manual selections. New ItemIds were added alphabetically. SORT sorted Rarity descending and retained the previous order for equal Rarity. It never compared Element priority. Consequently alphabetical IDs (including ELECTRIC before FIRE / ICE) and previous inventory order could prevent Fire→Ice→Electric.

Client findResult also performed its own candidate scan. The authoritative service instead validates ItemId structure, Mergeable, TypePrefixes, ElementSet, next Rarity, and exact result definition. The new UI removes that duplicate candidate/eligibility logic.

## Authoritative rules retained

- Regular items only; same ItemId ×3 → same Type / Element, next Rarity ×1. Legendary is not mergeable.
- CanMerge validates real Player, loaded data, saving state, count and result overflow.
- MergeItem calls CanMerge again, then RunItemTransaction → RemoveItem / AddItem → ChangeItemCounts → ResolveItemMutation. Existing atomic save and returned inventory state remain authoritative.
- Counts are stored by ItemId, without per-copy identity, grades or individual attributes. There is no random choice or meaningful alternative set of three copies. Socket 1 through RequiredCount represent the selected ItemId's available count. Equipped copies are not newly excluded.
- ItemMergeService, ItemService, PlayerDataService, ItemMaster, RequiredCount, Inventory notification logic and other tab code are unchanged.

## New flow

1. Large アイテムを選択する.
2. One card per owned eligible ItemId, image / name / Element / Rarity / count. Explicit Fire=1, Ice=2, Electric=3; Master.RarityRank ascending; Master.Kinds; ItemId tie-break.
3. Selected item and automatic Socket 1–3, count and MERGE. Missing sockets show ?. Server CanMerge controls enabled state; stale/failed state and pending requests disable it.

Back navigates 3→2→1; existing X closes Inventory. Reopening Merge starts at 1. Success retains the existing Merged result message, requests fresh server state, and keeps the same base item even at zero remaining count. No client inventory mutation exists. Read-only ItemMergeState delegates to the exact existing service methods.
